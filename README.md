### 4.2 The three gates, and what each one measures


| Gate                    | When         | Who     | What they are told to look at                                    | Therefore you must have                                                                                            |
| ----------------------- | ------------ | ------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **Eval 1** (mentorship) | Day 1, 18:30 | Mentors | "initial approach, **architecture**, and **technology choices**" | A 1-page architecture diagram + a coherent reason for each choice. Say it out loud in 60 seconds                   |
| **Round 1**             | Day 2, 08:00 | Jury    | "**core functionality and progress**"                            | **One complete vertical slice working end-to-end.** Not a mockup. Core path: input → processing → stored → visible |

### 4.3 Inferred scorecard (label this as inference when you use it)

Published criteria, mapped to how judges typically allocate weight. **Use this to allocate your own effort, and adjust once they announce weights at the event.**


| Criterion               | Working weight | What earns full marks                                                                                        | Where most teams lose                                             |
| ----------------------- | -------------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| **Innovation**          | ~20%           | A mechanism nobody else in the room is building; a clear "why this is new" in one sentence                   | ChatGPT wrapper with a new skin; "AI dashboard"                   |
| **Technical execution** | ~25%           | Real backend, real DB, real auth, typed code, clean git history, deployed, no dead buttons                   | Frontend-only with hardcoded arrays; broken flows discovered live |
| **Completeness**        | ~20%           | Every promised feature actually works end-to-end; error/empty/loading states; no TODOs visible in the demo   | Half-built features; "we'll finish that tomorrow"                 |
| **Design**              | ~15%           | Consistent, responsive, readable at 3m from a projector; sensible information hierarchy; smooth, no jank     | Default Tailwind look, tiny fonts, unstyled states                |
| **Presentation**        | ~20%           | 20-second hook, live demo that does not fail, honest architecture story, clear team attribution, handled Q&A | Reading slides, apologies for missing features, no metric         |


> **The uncomfortable truth:** a technically superior project with a bad 15:30 demo loses to a good project with a great demo. Both matter. Protect the demo.



### 4.4 Rubric → engineering checklist

- [ ] Innovation: one sentence, no jargon, that a non-technical judge could repeat to a friend
- [ ] Technical execution: deployed URL, real DB rows you can show, git history starting 15:30 Day 1
- [ ] Completeness: run through every button in front of a teammate before Round 1
- [ ] Design: test at 1366×768 (projector) and 390px (phone); min 16px body text
- [ ] Presentation: 3-minute script with a 20-second hook, rehearsed 3×, 90-second backup video on a laptop AND a phone

## 6. Track selection — the decision you make at 13:30



### 6.1 The competition math (reasoning, not published data)

- **Open** is the default choice for nervous teams. Highest team count → lowest odds of podium in any scenario where prizes are per-track.
- **Agentic AI** is the 2026 buzzword. Every second team will be in it. Highest team count, likely the fattest individual prize, but **the hardest podium to win**.
- **Decentralized Intelligence** was swapped in rat the last minute (was "Surprise"). Fewer teams will have prepared for it. Solidity/federated learning is a real barrier → the field self-selects smaller. **Best odds of a podium spot**, provided your team can actually ship it.



### 6.2 Recommendation


| Your team                                         | Pick                           | Why                                                                                |
| ------------------------------------------------- | ------------------------------ | ---------------------------------------------------------------------------------- |
| 4 devs, ≥1 comfortable in TS + 1 in Python        | **Decentralized Intelligence** | Fewest competitors, clearest differentiation, sponsor/judge attention. Highest EV  |

### 7.6 Offline / failure-proofing the stack

- Run a local fallback stack so a Wi-Fi outage never kills the demo:
`Docker Desktop` (Postgres + pgvector) + **Ollama** (local model) + SQLite file + pre-seeded fixtures.
- **Pre-seed everything.** The demo dataset must exist in the DB before you walk on stage.
- **Fixture layer:** a single `DEMO_MODE=true` env flag that returns recorded responses instead of live model calls. Switch to live only if the network is healthy.
- Download node modules, model files, and datasets **before** leaving for the venue.

### 8.1 TRACK 01 — OPEN · "FixLens: civic issue reporting with proof of fix"

**One-liner:** A civic issue reporting platform where every report is agent-triaged, publicly tracked, and can only be marked resolved with geo-tagged proof plus community verification.

**The problem (why it's not just another complaint app):** civic apps fail because nobody verifies resolution and nobody is accountable. FixLens closes the loop and makes resolution a *verifiable event*.

**Why judges like it:** real civic impact, a live map demo, and a measurable metric ("duplicate reports collapsed", "median time-to-resolution", "% resolved with verified proof").

**Features**


| Must-have (build first)                                                                      | Nice-to-have (only after 23:00 Day 1)          |

### 8.2 TRACK 02 — AGENTIC AI · "CiteProof: multi-agent audit with an evidence graph and an adversarial verifier"

**One-liner:** A team of specialised agents that produces a decision-grade report, where **every claim is bound to evidence**, and a separate **adversarial agent actively tries to falsify the report** before a human approves it.

**The problem:** the entire room will build "chatbot + document". This builds the thing that is actually missing: **verifiable, auditable, falsifiable agent output**. It matches the track description word-for-word — *autonomous agents, multi-agent workflows, intelligent decision-making systems*.

**The three-part mechanism (this is your differentiator):**

1. **Orchestration graph** (LangGraph): `Intake → Retrieve → Analyse → Cite → RedTeam → Synthesise → Human-gate` with explicit state, checkpointing, and a **human-in-the-loop interrupt** before publish.
2. **Evidence graph:** each claim node links to the exact source span (quote + page + offset). Click a claim → see the evidence. Claims with no evidence are *flagged*, not hidden.
3. **Adversarial verifier:** a red-team agent whose only job is to refute claims. Where it succeeds, the claim is downgraded or removed — and the UI shows the refutation.

**Features**


| Must-have                                                              | Nice-to-have                                    |
| ---------------------------------------------------------------------- | ----------------------------------------------- |
| LangGraph pipeline with checkpointing + 1 human-in-the-loop gate       | Streaming trace viewer (Langfuse → your own UI) |
| Structured claim output with citations (Zod schema, enforced)          | Cost/latency panel per agent step               |
| Claim → evidence click-through with source highlights                  | Adversarial "steelman" mode                     |
| Red-team agent that outputs refutations with confidence                | Export to signed PDF report                     |
| Live trace visualiser (the graph, coloured by pass/fail)               | Replay a run from the checkpoint                |
| Seeded corpus (e.g. policy docs / research papers / municipal notices) | Compare two agents' reports side-by-side        |


**Architecture:** LangGraph (Python, `uv`) + FastAPI behind a typed contract · Next.js + shadcn/ui + React Flow (or a hand-rolled SVG graph) for the trace view · Supabase pgvector for retrieval + Postgres for claims/evidence · Langfuse tracing · Vercel AI SDK for streaming into the UI.

**3-minute demo script:** ask a real question → watch the graph light up agent by agent in the UI → open the report → click a claim, see the exact quoted evidence highlighted in the source PDF → trigger the red-team agent, watch it kill one weak claim live → approve through the human gate → show the trace with token cost and latency per step.

**Rubric mapping:** innovation = falsification + evidence graph (nobody else will build this today) · technical execution = real graph orchestration, checkpoints, human-in-the-loop · completeness = full run lifecycle + failure handling · design = graph/trace UI is visually impressive · presentation = "watch it kill my own claim" is a memorable 5 seconds.

**Critical mitigations:** pre-warm and cache all demo runs; set temperature 0; short prompts; if a model call exceeds 6s in the demo, fall back to the recorded run (build the fixture flag in from hour 1, not at 06:00 Day 2).

### 8.3 TRACK 03 — DECENTRALIZED INTELLIGENCE · "AgentTrust Ledger: verifiable reputation + escrow for autonomous agents"

**One-liner:** A decentralised registry where AI agents publish a signed identity (model, prompt, policy hash), build on-chain reputation from verified task performance, and transact through escrow with **fraud proofs and slashing** — so an agent that lies or fails gets destroyed automatically.

**The problem:** as agents act autonomously, nobody can verify *what model ran*, *what it was told*, or *whether it can be trusted*. The track text literally asks for systems "where data, models and decisions are shared across many participants".

**The three-part mechanism:**

1. **Signed agent registry (contract):** an agent registers `{owner, modelHash, promptHash, policyHash, capabilities}`. Content hashes published to IPFS. Any change = new version, old reputation stays with the old version (reputation is per-version, which is the honest design).
2. **Escrow with dispute + slashing (contract):** agent A hires agent B for a task; payment is escrowed; a verifier submits a result; if challenged within a window, a dispute resolves and a losing party loses a slashable stake.
3. **Off-chain execution, on-chain truth (service + subgraph):** the agent runtime runs off-chain (Python/TS), each step is signed, results are hashed and anchored on-chain so the chain holds *proof of execution* without holding data.

**Features**


| Must-have                                                                             | Nice-to-have                                         |
| ------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| `AgentRegistry.sol` — register/version agents with content hashes                     | Reputation decay over time                           |
| `EscrowDispute.sol` — pay → deliver → verify → release, with slash on failure         | On-chain leaderboard UI with animations              |
| `Reputation.sol` — score per agent version, decayed on failed delivery                | Multi-sig / DAO governance of dispute rules          |
| Hardhat/Foundry tests (even 6 tests prove engineering)                                | Off-chain signer service for step-level attestations |
| viem + wagmi frontend: register agent → hire agent → watch escrow state machine       | IPFS metadata viewer                                 |
| One complete demo path: register → hire → deliver → dispute → slash → reputation drop | GraphQL indexer (The Graph / Ponder)                 |
| Testnet only (Base Sepolia), seeded agents so the map is not empty                    |                                                      |


**Architecture:** Foundry (Solidity, `forge test`) · viem + wagmi + RainbowKit/Reown · Next.js + Supabase for off-chain agent runtime + indexed reads · Base Sepolia · Ponder or Graph-node for reads (only if time).

**3-minute demo script:** register an agent in the UI (type a prompt, it hashes and signs) → it appears in the registry with its model/prompt hashes → hire it for a micro-task → escrow locks → deliver result → challenger disputes → the contract resolves and **slashes** the failing agent → watch its reputation drop live on the leaderboard.

**Rubric mapping:** innovation = per-version reputation + fraud proofs · technical execution = real contracts, tests, state machine, testnet · completeness = full lifecycle including the failure path (the failure path is what makes it credible) · design = leaderboard + state transitions · presentation = "watch money get slashed automatically" is the demo.

**Fallback (if Solidity is too risky — do NOT attempt Foundry and a complex app solo):** the **Federated & Edge AI** route — simulate FedAvg across N simulated edge clients, sign each client's gradient update with a keypair, aggregate into a Merkle root, anchor the root on-chain, and show poisoning detection (an outlier client gets quarantined). Same track, no contract debugging, still deep.
